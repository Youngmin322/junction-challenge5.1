# 팀 운영·멘토·이해관계자 협업

> [!abstract] 핵심
> CBL의 개방성은 역할 없음이 아니다. 러너가 방향과 결정을 소유하되, 팀은 명확한 운영 규칙을 만들고 멘토는 답 대신 질문·연결·피드백을 제공하며 이해관계자는 단순 인터뷰 대상이 아니라 현실성과 영향의 공동 검토자가 된다.

관련 문서: [[00 CBL 러너 플레이북]] · [[02 Engage 실전 가이드]] · [[05 기록·성찰·공유와 학습 증거]] · [[08 Challenge 6 헬스케어 적용 가이드]]

## 1. 역할의 기본 원칙

| 참여자 | 책임 | 하지 말아야 할 일 |
|---|---|---|
| 러너 | 질문·조사·판단·실험·성찰을 소유 | 멘토의 정답을 기다리기 |
| 팀 | 관점과 능력을 결합하고 상호 책임을 만든다 | 일을 개인별로 분리한 뒤 마지막에 합치기 |
| 멘토·퍼실리테이터 | 과정, 질문, 기준, 연결, 안전을 지원 | Challenge와 솔루션을 대신 결정하기 |
| 주제 전문가 | 정확성·현장 맥락·위험을 검토 | 모든 사용자와 조직을 대표한다고 가정하기 |
| 이해관계자 | 경험·제약·영향·실행 조건을 제공 | 형식적인 승인 도장 역할만 하기 |
| 의사결정자·기관 | 권한·자원·정책·승인 경로를 명확히 함 | 비공식 관심을 공식 승인처럼 표현하기 |

역할은 고정 직책보다 현재 학습 필요에 따라 유동적으로 바뀔 수 있다. 그러나 매 활동의 책임자는 한 명으로 명시한다.

## 2. 팀을 시작할 때 합의할 것

### 2.1 Team Norms

- 코어 타임과 응답 기대 시간
- 회의 시작·종료 규칙
- 준비가 안 되었을 때 알리는 방식
- 반대 의견을 제시하는 방식
- 결정 방식과 결정권자
- 기록 위치와 파일명
- 지각·미완료·갈등의 복구 절차
- 집중 시간과 비동기 작업의 경계
- 민감 정보의 공유 금지선

규칙은 “서로 존중한다”보다 관찰 가능한 행동으로 쓴다.

나쁜 예: `적극적으로 소통한다.`  
좋은 예: `진행을 막는 위험은 발견 후 다음 코어 타임 전까지 공용 보드에 올리고 책임자에게 알린다.`

### 2.2 강점·성장 목표 지도

각 팀원이 다음을 공개한다.

- 제공할 수 있는 기술·관계·경험
- 이번 Challenge에서 배우고 싶은 능력
- 피하고 싶지만 연습해야 하는 역할
- 에너지와 시간 제약
- 피드백을 받기 편한 방식

업무를 항상 가장 잘하는 사람에게만 배정하면 제품은 빨라져도 러너의 성장은 멈춘다. 위험이 낮은 활동에서는 성장 목표에 따라 역할을 순환한다.

## 3. 의사결정 방식을 미리 정한다

| 방식 | 적합한 상황 | 주의점 |
|---|---|---|
| 책임자 결정 | 빠르고 되돌릴 수 있는 실무 결정 | 근거와 이견 기록 |
| 자문 후 책임자 결정 | 전문성 또는 영향이 여러 곳에 있음 | 자문을 합의로 오해하지 않기 |
| 동의 기반 | 팀 규칙·Challenge·윤리 경계 | 반대 이유와 수정 조건 확인 |
| 실험으로 결정 | 의견 충돌을 관찰로 판별 가능 | 사전 판정 기준 필요 |
| 권한자 승인 | 병원·법무·개인정보·예산 등 | 비공식 피드백과 공식 승인을 구분 |

모든 것을 만장일치로 하면 중요한 결정을 피하게 된다. 결정 유형별 책임과 재검토 조건을 둔다.

## 4. 회의는 상태 보고가 아니라 판단 공간이다

### 4.1 60분 코어 타임 예시

| 시간 | 활동 |
|---:|---|
| 5분 | 오늘 내려야 할 결정 확인 |
| 10분 | 새 증거와 바뀐 가정 공유 |
| 20분 | 핵심 질문 또는 충돌 분석 |
| 15분 | 대안·실험·결정 |
| 5분 | 책임자·기한·완료 기준 |
| 5분 | 팀 상태와 짧은 성찰 |

상태 업데이트는 가능한 한 비동기로 한다. 회의 초대에는 `목적`, `결정할 질문`, `사전 자료`, `참여자가 필요한 이유`를 쓴다.

### 4.2 네 개의 보드

- **질문 보드**: 지금 답해야 할 Guiding Questions
- **증거 보드**: 지지·반박·불충분 자료
- **결정 보드**: 확정·보류·재검토 조건
- **행동 보드**: 책임자·기한·완료 정의

아이디어 보드 하나만 커지고 나머지가 비어 있으면 솔루션 편향 신호다.

## 5. 심리적 안전과 지적 긴장을 함께 만든다

심리적 안전은 모든 의견에 동의하는 상태가 아니다. 사람을 공격하지 않으면서 가정과 근거를 강하게 검토할 수 있는 상태다.

사용할 문장:

- “그 결론을 지지하는 관찰은 무엇인가요?”
- “반대 사례가 있다면 무엇일까요?”
- “이것은 사실, 해석, 선호 중 무엇인가요?”
- “누가 이 결정의 비용을 부담하나요?”
- “결정을 뒤집을 증거는 무엇인가요?”
- “아직 말하지 않은 우려를 각자 한 가지씩 적어봅시다.”

피할 문장:

- “다들 괜찮죠?”
- “전문가가 그랬으니 맞아요.”
- “일단 만들고 봅시다.”
- “그건 부정적인 태도예요.”

## 6. 갈등을 다루는 절차

1. 사람과 쟁점을 분리한다.
2. 각자의 관찰 사실과 이해를 독립적으로 적는다.
3. 공통 목표와 결정 시한을 확인한다.
4. 충돌하는 가정·가치·자원 제약을 구분한다.
5. 증거로 판별 가능한 것은 작은 조사·실험으로 바꾼다.
6. 가치 또는 책임 충돌은 합의된 결정권자가 판단한다.
7. 결정과 소수 의견, 재검토 조건을 기록한다.
8. 관계에 미친 영향을 별도로 회복한다.

반복되는 미완료는 태도 평가 전에 업무 크기, 완료 기준, 의존성, 시간 제약을 점검한다.

## 7. 멘토를 효과적으로 활용한다

### 7.1 멘토링 전 보낼 한 장

- 현재 Challenge
- 이번 주에 새로 알게 된 것 3개
- 가장 불확실한 가정 1–3개
- 고민 중인 결정과 대안
- 이미 시도한 것
- 멘토에게 원하는 도움: 질문, 기준 검토, 연결, 위험 검토 중 하나

“어떻게 해야 할까요?”보다 구체적인 판단 질문을 보낸다.

예:

> 환자 직접 인터뷰 없이 퇴원 후 돌봄의 문제 구조를 먼저 검증하려 합니다. 의료진 인터뷰와 공개 자료로 확인할 때 놓치기 쉬운 반대 관점과, 실제 환자 연구로 넘어가기 전 필요한 승인 경로를 검토해 주세요.

### 7.2 멘토 피드백을 처리하는 법

- 피드백을 `사실`, `전문가 판단`, `가설`, `연결 기회`, `요구사항`으로 분류한다.
- 한 전문가의 의견을 전체 현장의 사실로 일반화하지 않는다.
- 채택·보류·반박 여부와 이유를 결정 로그에 남긴다.
- 상충하는 피드백은 맥락 차이를 확인하거나 추가 증거를 찾는다.

멘토의 권위가 팀의 학습 소유권을 대신하지 않는다.

## 8. 이해관계자를 찾고 우선순위화한다

### 8.1 네 가지 축

- 문제의 영향을 직접 받는가?
- 실행 권한 또는 자원을 갖는가?
- 현장 지식 또는 안전 책임을 갖는가?
- 현재 접근 가능하며 참여 부담을 통제할 수 있는가?

### 8.2 관계 수준

| 수준 | 목적 | 예시 |
|---|---|---|
| 정보 제공 | 프로젝트와 요청을 투명하게 설명 | 한 장 소개 |
| 자문 | 맥락·가정·위험 검토 | 전문가 인터뷰 |
| 공동 탐색 | 질문·통찰·기준을 함께 형성 | 워크숍 |
| 공동 실험 | 프로토타입과 평가를 함께 설계 | 제한된 모의 파일럿 |
| 공동 소유 | 운영·유지·의사결정을 분담 | 공식 파트너십 |

첫 만남부터 공동 소유를 기대하지 않는다. 신뢰, 역할, 승인 범위를 단계적으로 높인다.

## 9. 첫 접촉 메시지의 구조

1. 우리는 누구인가?
2. 왜 이 사람에게 연락했는가?
3. 현재 탐색 중인 Challenge는 무엇인가?
4. 아직 결론 내리지 않은 것은 무엇인가?
5. 구체적으로 무엇을 요청하는가? 시간·형식·주제
6. 민감 정보나 환자 정보를 요청하지 않는다는 경계
7. 참여하지 않아도 불이익이 없다는 점
8. 결과를 어떻게 공유할 것인가?

예시:

> 저희는 Apple Developer Academy의 러너 팀으로, 퇴원 이후 돌봄 연속성에서 발생하는 정보·행동·업무 흐름의 간극을 탐색하고 있습니다. 특정 앱을 제안하기보다 현재 과정을 이해하려 합니다. 30분 동안 일반적인 퇴원 교육과 후속 관리 흐름, 현장에서 느끼는 장벽을 여쭙고 싶습니다. 환자 식별 정보나 진료 기록은 요청하지 않으며, 기록 방식과 인용 범위는 사전에 확인드리겠습니다.

## 10. 인터뷰를 관계로 전환한다

만남 뒤 24–48시간 내에:

- 감사와 합의한 인용·공유 범위 확인
- 이해한 내용을 3–5문장으로 되돌려 확인
- 해결되지 않은 질문과 다음 요청을 구분
- 약속한 자료 전달
- 프로젝트 방향이 바뀌면 관련 이해관계자에게 알림

“인터뷰 수”보다 약속 이행과 정확한 재현이 신뢰를 만든다.

## 11. 권한·대표성·보상

- 전문가 한 명은 기관 전체를 대표하지 않는다.
- 접근하기 쉬운 사람만 만나면 영향은 크지만 목소리가 약한 집단이 누락된다.
- 참여자의 시간과 정서적 부담을 설계에 포함한다.
- 가능한 경우 보상·감사·결과 환류 방식을 기관 정책에 맞춰 정한다.
- 이해관계자가 반대하거나 참여를 중단할 권리를 보장한다.
- 건강·취약성·고용 관계가 있으면 자발적 동의가 실제로 가능한지 더 엄격하게 본다.

## 12. 파트너십과 승인을 구분한다

다음 문장은 서로 다르다.

- “한 의사가 아이디어가 흥미롭다고 했다.”
- “담당 부서가 연구 질문을 검토했다.”
- “기관이 제한된 테스트를 공식 승인했다.”
- “기관과 역할·책임·데이터 처리를 정한 협약이 있다.”

외부 발표와 팀 기록에서 현재 수준을 정확히 표현한다. 명함 교환이나 긍정적 대화는 기관 승인 또는 협업 확정이 아니다.

## 13. Challenge 6 팀 운영 제안

현재 합의된 평일 `14:30–15:30` 코어 타임을 다음처럼 사용한다.

### 월요일: 학습 방향

- 지난주 증거와 열린 질문
- 이번 주 최우선 Guiding Questions 1–3개
- 외부 접촉·안전·승인 필요 확인

### 화–목요일: 조사·실험

- 새 증거 10분
- 핵심 분석 또는 준비 35분
- 결정·책임·기록 15분

### 금요일: 통합과 성찰

- 결론·가정 신뢰도 갱신
- 다음 주 이해관계자 요청
- 팀 Norms 점검과 개인 학습 증거 정리

S-Pohang Hospital은 현실적인 첫 접점일 수 있지만 최종 문제·사용자·솔루션을 정당화하는 유일한 출처가 아니다. 개인 의료진과의 협업, 병원 조직의 공식 승인, 환자 연구는 서로 다른 관계·권한 수준으로 관리한다. 자세한 현황은 [[08 Challenge 6 헬스케어 적용 가이드]]에 정리한다.

## 14. 협업 품질 게이트

- [ ] 팀 규칙이 관찰 가능한 행동으로 쓰였다.
- [ ] 결정 유형별 책임자와 방식이 명확하다.
- [ ] 역할이 학습 목표와 위험 수준에 맞게 배정된다.
- [ ] 회의마다 결정·행동·기한이 남는다.
- [ ] 반대 의견과 누락 관점을 안전하게 제시할 수 있다.
- [ ] 멘토 피드백을 근거 유형별로 분류하고 팀이 판단한다.
- [ ] 이해관계자의 참여 목적·부담·동의 범위가 명확하다.
- [ ] 개인 의견과 기관의 공식 승인을 구분한다.
- [ ] 외부 약속의 책임자와 후속 조치가 기록된다.
- [ ] 협업 과정 자체가 개인·팀 학습 증거로 남는다.
